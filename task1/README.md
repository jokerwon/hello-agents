## 6. 习题

### 6.1 本章介绍了三种经典的智能体范式:ReAct、Plan-and-Solve 和 Reflection。请分析:

### 6.1.1 这三种范式在"思考"与"行动"的组织方式上有什么本质区别？

本质区别在**决策时机**与**纠错信号源**两个维度。

| 维度             | ReAct                                                | Plan-and-Solve                                                 | Reflection                                           |
| ---------------- | ---------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| 思考与行动的关系 | **交错**：每一步都是"先想后做"，思考只为当前一步负责 | **分离**：思考集中在规划阶段一次性完成，执行阶段原则上不再思考 | **回看**：行动已完成后再思考，思考的对象是行动的产物 |
| 决策时机         | 滚动式（step-by-step，无全局承诺）                   | 前置式（先承诺完整计划，再机械执行）                           | 事后式（post-hoc，对输出做迭代校正）                 |
| 纠错信号源       | **外部**：环境返回的 Observation 驱动下一步调整      | **无**：计划是静态的，执行中不纠偏（见 6.4.1）                 | **内部**：自我批判产生的 Feedback 驱动重写           |
| 上下文的角色     | 不断增长的轨迹（行动-观察对），是"记忆"              | 计划作为常驻"宪法"，历史结果是状态链                           | 执行-反思轨迹构成"短期记忆"，供下一轮迭代引用        |
| 典型失败模式     | 局部最优、原地打转、格式漂移                         | 计划一步错、后续全错；无法应对执行期意外                       | 不收敛（越改越差）、成本失控、评审标准漂移           |
| 成本结构         | 串行多轮调用，延迟与步数成正比                       | 规划 1 次 + 执行 n 次，可并行化潜力大                          | 每轮迭代 ≥2 次额外调用，串行依赖                     |

ReAct 用行动获取思考的依据，Plan-and-Solve 用思考预先消除行动的不确定性，Reflection 用思考事后检验行动的质量。

### 6.1.2 如果要设计一个"智能家居控制助手"（需要控制灯光、空调、窗帘等多个设备，并根据用户习惯自动调节），你会选择哪种范式作为基础架构？为什么？

以 ReAct 为基础架构。

1. **任务特性是短链路、强实时、依赖当前状态**。"把客厅调到 24 度"这类指令，从意图到执行只有 1-3 步，且每一步的决策依据是**实时的环境观察**（传感器温度、光照、人在不在家）——这正是 ReAct 的 Observation 循环的用武之地。Plan-and-Solve 的"先出完整计划再执行"在这里是过度设计：为一个两步操作生成计划徒增延迟。
2. **需要动态纠错**。开灯后发现窗帘没关、空调与新风冲突——ReAct 可以根据每步执行后的观察（如"温度仍为 27°C"）调整下一步动作；静态计划做不到。
3. **可解释性对家用场景重要**。Thought 轨迹让"为什么自动关了卧室灯"有据可查，是用户信任的基础。

### 6.1.3 是否可以将这三种范式进行组合使用？若可以，请尝试设计一个混合范式的智能体架构，并说明其适用场景。

```
用户问题
   │
   ▼
① Planner（Plan-and-Solve 的规划层）—— 生成子任务序列，保证全局结构
   │
   ▼
② 逐子任务运行 ReAct 智能体 —— 子任务内自主调用工具（搜索/计算），
   │   遇到外部信息需求时动态交互、即时纠错
   ▼
③ Reflection 终检 —— 审视组合答案的完整性/一致性，发现问题则修订
   │
   ▼
最终答案
```

**适用场景**：任何"结构复杂 + 需要外部信息 + 质量敏感"的任务——调研报告、旅行规划、客服工单处理等。

### 6.2 在4.2节的 ReAct 实现中，我们使用了正则表达式来解析大语言模型的输出（如 Thought 和 Action）。请思考:

### 6.2.1 当前的解析方法存在哪些潜在的脆弱性？在什么情况下可能会失败？

1. **`(\w+)` 不兼容现实工具名**：连字符（`order-query`）、点号（`db.query`）都匹配失败 → 整轮浪费。
2. **贪婪匹配污染参数**：`(.*)` 贪婪到**最后一个** `]`。当模型输出幻觉 Observation、连发两个 Action、或 Action 后附带含 `]` 的解释文字时，工具输入被吞入大量垃圾内容、且 Finish 指令丢失（`Search[...]` 的参数里混入了编造的观察结果和 `Finish[得主是A与B。]`）。
3. **Finish 不带方括号时静默返回空答案**：`Action: Finish 答案是...` 通过了 `startswith("Finish")` 检查，但 `_parse_action_input` 正则不匹配返回 `""`——智能体"成功"结束却交付了空字符串，**没有任何报错**。这是最危险的一类：静默失败。
4. **多 Action 时只取第一个**：`re.search` 锚定首个 `Action:`，后面的被丢弃或污染前者。
5. **无法做语义/类型校验**：正则只管形态，不管 `action_input` 是否为空、是否是字符串、工具是否存在——这些都留到运行期才爆炸。
6. **协议本身脆弱**：模型换一个（指令遵循能力不同）、temperature 调高、提示词微调一个词，格式遵循率就会漂移；中文标点（`：`）、CRLF 换行、markdown 加粗都会产生边角 case。

**何时失败**：弱模型/小模型、低 temperature 未开启、多工具复杂协议、长历史（模型开始"复述"格式）、工具参数本身含 `]` 或换行（如 JSON 参数、多行代码）。

### 6.2.2 除了正则表达式，还有哪些更鲁棒的输出解析方案？

| 方案                                       | 原理                                                                                                              | 保证强度           | 通用性               |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------ | -------------------- |
| **JSON 协议 + 容错解析**（本文实现）       | 提示词要求输出单一 JSON；解析端做括号平衡扫描（容忍围栏/前后缀）、字段校验、失败时把错误作为 Observation 反馈重试 | 中（依赖模型遵循） | 任何 OpenAI 兼容网关 |
| **Pydantic/JSON Schema 校验**              | 在上一条之上加 schema 级校验（类型、必填、枚举），错误信息可精准回喂                                              | 中强               | 同上                 |
| **Function Calling / Tool Use API**        | 把工具定义成 API 参数，由服务端生成结构化 `tool_calls`，客户端不再解析自由文本                                    | 强                 | 需网关支持           |
| **Structured Outputs（JSON Schema 强制）** | 服务端用受限解码保证输出 100% 符合 schema（OpenAI 2024-08 起支持 `response_format=json_schema`）                  | 最强               | 需模型方支持         |
| **语法约束解码（GBNF/Outlines/guidance）** | 本地推理时用文法限制采样，语法层面不可能产生非法输出                                                              | 最强               | 仅本地推理           |
| **Few-shot 示例 + 自愈循环**               | 示例锚定格式 + 解析失败自动重试                                                                                   | 弱中（经验性）     | 通用，常与上列组合   |

工程上的组合拳：**优先用 Function Calling / Structured Outputs（有能力就用）→ 退而求其次 JSON 协议 + schema 校验 + 带反馈重试 → 少样本示例提升首次遵循率**。

把输出协议改为单一 JSON 对象 {"thought", "action", "action_input"}，解析时括号平衡扫描，容忍 markdown 围栏与前后缀文字 + 字段校验 + 失败反馈重试。

### 6.3.2 设计并实现一个"工具选择失败"的处理机制:当智能体多次调用错误的工具或提供错误的参数时，系统应该如何引导它纠正？

1. **结构化错误 Observation**：区分三类失败（工具不存在 / 参数为空 / 工具拒绝参数），每类都返回**可操作的**引导信息，而不是笼统的"出错了"。
2. **拼写纠错建议**：工具不存在时用 `difflib.get_close_matches` 给出最接近的可用工具名——实测模型拼出 `Calculatorr` 时，观察返回"你是不是想用 'Calculator'？"，下一轮即纠正。
3. **参数提示回喂**：注册工具时附带 `param_hint`；参数被拒时把 param_hint 塞进 Observation（且工具描述本身就含参数要求，从源头减少错误）。实测模型传"请帮我算一下那道题"时，观察返回了拒绝原因 + 完整参数要求。
4. **升级引导（few-shot 注入）**：连续失败 ≥2 次时，把一条**正确调用的完整示范**（含期望的 Observation）注入历史——实测注入后真实 LLM 立即按示范格式调用成功。
5. **安全熔断**：连续失败 ≥4 次抛出 `RuntimeError` 终止本轮，防止在错误循环里烧 token——实测持续错误调用在第 4 次触发熔断，带完整失败日志优雅退出。

### 6.3.3 思考:如果可调用工具的数量增加到50个甚至100个，当前的工具描述方式是否还能有效工作？在可调用工具数量随业务需求显著增加时，从工程角度如何优化工具的组织和检索机制？

**很难有效工作**

1. **Token 成本线性膨胀**：每工具描述约 30~80 token，100 个工具意味着每次调用携带 3~8k token 的工具清单，且 ReAct 每一步都要重复注入——成本与延迟双杀。
2. **选择准确率下降**：工具越多，描述之间的区分度越低（"查询订单"vs"查询历史订单"），模型的注意力被稀释，误选率上升；工具描述之间还会互相干扰。
3. **维护治理失控**：重名/近义工具、过时描述、无人使用的僵尸工具会持续污染选择空间。

**优化方案**：

1. **工具检索（Tool RAG）**：为工具的名称+描述+参数 schema 建立向量索引，运行时按用户问题检索 Top-K（如 10 个）动态注入提示词。这是百级工具的事实标准方案（MCP 生态的工具过滤、OpenAI 的 function calling 都在往这个方向演化）。
2. **分层/命名空间组织**：按业务域分组（订单域/物流域/售后域），两阶段选择——先让模型（或一个小分类模型）选工具域，再在域内精确选择，把 100 选 1 变成 10 选 1 × 10 选 1。
3. **规范注册 + 自动描述**：用 OpenAPI/JSON Schema 定义工具，描述由元数据自动生成并统一格式，配合 lint 检查描述质量（区分度、长度、参数说明完整性）。
4. **按需懒加载 + 会话缓存**：工具按场景动态注册（当前任务只挂载相关工具），会话内保持工具集稳定。
5. **工具路由小模型**：用一个廉价分类模型先做粗筛，主模型只在候选集里决策。
6. **度量与治理**：监控每个工具的选择率/误选率/失败率，淘汰低使用工具，定期用"工具选择准确率"测试集做回归。

### 6.4 Plan-and-Solve 范式将任务分解为"规划"和"执行"两个阶段。请深入分析:

### 6.4.1 在其实现中，规划阶段生成的计划是"静态"的（一次性生成，不可修改）。如果在执行过程中发现某个步骤无法完成或结果不符合预期，应该如何设计一个"动态重规划"机制？

**1. 失败检测（Detect）**——失败必须显式上报而不是靠猜：

- 显式信号：执行器提示词中加入规约——"步骤确实无法完成时，回复必须以 `STEP_FAILED: 原因` 开头，禁止编造数据假装完成"；
- 隐式信号：执行结果为空视为失败（兜底）；
- （可扩展：结构化输出的 schema 校验失败、工具返回的错误码、超时。）

**2. 重规划（Replan）**——只重规划"剩余工作"：把 原问题 + **已完成步骤及结果** + 失败步骤 + 失败原因 + 原剩余步骤 交给规划器，生成新剩余计划；已完成的结果**原样保留**（不重复劳动、信息不丢失），新计划拼接在已完成部分之后继续执行。

**3. 预算控制（Budget）**：`max_replans=2` 限制重规划次数防死循环；额度用尽仍失败则带着部分结果优雅终止，而不是整体作废。

### 6.4.2 对比 Plan-and-Solve 与 ReAct:在处理"预订一次从北京到上海的商务旅行（包括机票、酒店、租车）"这样的任务时，哪种范式更合适？为什么？

**结论：以 Plan-and-Solve 为骨架、子任务内用 ReAct 的混合架构最合适（即 6.1.3 的架构）；若只能二选一，选 Plan-and-Solve。**

分析："预订北京→上海的商务旅行（机票+酒店+租车）"的任务特征是：

- **多目标、强约束、全局耦合**：预算上限、会议时间窗、机场与酒店的区位匹配（虹桥vs浦东）、租车取还时间要衔接航班——这些约束横跨所有子任务，**必须在全局层面统筹**。ReAct 的步进式决策"走一步看一步"，极易陷入局部最优：先订了早班机，后面才发现酒店只能下午入住、租车门店那个时间已打烊。
- **子任务内部高度动态**：查询航班发现没有合适时段、酒店满房需要换区域——这些需要**实时查询与即时调整**，是静态计划做不到的。

所以：**Plan 层负责把"预算/时间/区位"的全局约束编进计划**（例如"先定航班，再按到达机场选酒店区域，最后按酒店位置选租车门店"这个顺序本身就是约束推导的结果）；**ReAct 层负责每个子任务内的搜索-比较-调整**；遇到子任务彻底失败（该时段无航班）则触发 6.4.1 的重规划。纯 ReAct 输在全局性，纯 Plan-and-Solve 输在应变力。

### 6.4.3 尝试设计一个"分层规划"系统:先生成高层次的抽象计划，然后针对每个高层步骤再生成详细的子计划。这种设计有什么优势？

```
高层规划器（战略层）："要完成什么" —— 2~4 个抽象阶段
   └─ 子规划器（战术层）：每个阶段展开为 2~3 个具体子步骤
        └─ 执行器（执行层）：逐叶子执行，阶段成果汇入全局历史
```

**优势**：

1. **关注点分离**：高层规划不被实现细节干扰（"调研优势"vs"去哪个网站查什么关键词"），更容易保持全局结构合理；
2. **上下文聚焦**：每次子规划/执行只处理本阶段的内容，提示词短、注意力集中——对比扁平计划把所有细节塞一个列表；
3. **可复用与可并行**：抽象阶段相互独立（本实现中阶段 1/2/3 无数据依赖时理论上可并行执行子计划），子计划可缓存复用；
4. **与 6.4.1 正交可组合**：分层规划解决"计划粒度"，动态重规划解决"计划失效"，二者叠加即生产级的规划系统。

### 6.5 Reflection 机制通过"执行-反思-优化"循环来提升输出质量。请思考:

### 6.5.1 在代码生成案例中，不同阶段使用的是同一个模型。如果使用两个不同的模型（例如，用一个更强大的模型来做反思，用一个更快的模型来做执行），会带来什么影响？

**正面影响**：

1. **质量上限由反思模型决定**：初稿谁都能写，但"发现 bool 是 int 子类导致类型检查失效"（我们的实测中强模型真实发现的问题）这类深水区问题，弱模型根本看不见。反思环节用强模型 = 把预算花在刀刃上。
2. **成本结构优化**：执行（生成代码/初稿）是 token 大户，用快而便宜的模型跑；反思是 token 小户但判断密度高，用强模型。典型配比下总成本反而下降。
3. **天然的异构分工**：这是生产系统常见模式（executor=小模型，reflector=旗舰模型），且反思模型可以独立升级而不动执行链路。

**负面影响与风险**：

1. **能力断层导致"改不动"**：强评审提出的高级改进（如"换用分段筛法"），弱执行者可能无法正确实现，甚至越改越错——迭代变成失败循环，且没有机制能发现"问题出在执行侧"。
2. **评分标尺漂移**：强模型的评分基准与弱模型自评不同。若终止条件依赖 score 阈值（见 6.5.2），换反思模型必须**重新校准阈值**，否则要么永不收敛（评分过严）要么提前放行（过宽）。
3. **风格与术语不一致**：评审反馈的术语体系弱模型未必对齐，反馈的"可操作性"下降。

**工程对策**：统一输出协议（JSON）+ 按模型校准阈值 + 反馈中强制附带"具体到代码行级别的修改指令"（降低对执行模型理解能力的要求）+ 监控每轮"反馈被采纳率"检测能力断层。

### 6.5.2 Reflection 机制的终止条件是"反馈中包含无需改进"或"达到最大迭代次数"。这种设计是否合理？能否设计一个更智能的终止条件？

**原条件的缺陷**："反馈包含'无需改进'子串"有两个硬伤——① **子串误判**：实测反馈"该代码功能正确，在算法层面已无需改进。但是变量命名晦涩、未处理 n<2 边界……"包含"无需改进"四个字，旧机制会**带着未修复的问题收工**；② **两态判定无度量**：无法表达"还有改进但收益递减"这类中间状态。而"最大迭代次数"是纯预算兜底，与质量无关。

**改进**：评审员输出结构化裁决 `{"verdict", "score", "issues", "suggestions"}`，终止策略组合四条规则（任一命中即停并给出**明确原因**）：

- **T1** 裁决为 `NO_IMPROVEMENT`（显式无改进空间）
- **T2** score ≥ 85（质量阈值）
- **T3** 迭代≥2 且本轮得分提升 < 3（收益递减——继续迭代不划算）
- **T4** 达到最大迭代次数（预算兜底）

### 6.5.3 假设你要搭建一个"学术论文写作助手"，它能够生成初稿并不断优化论文内容。请设计一个多维度的Reflection机制，从段落逻辑性、方法创新性、语言表达、引用规范等多个角度进行反思和改进。

**设计**：

```
草稿 ──► 4 个专职评审员（各自结构化打分）
           段落逻辑性 | 方法创新性 | 语言表达 | 引用规范
                    │  {"dimension", "score", "issues", "suggestions"}
                    ▼
          聚合器：全部维度 score ≥ 80 → 收敛终止；
                  否则把"按维度分组的问题清单"交给 Refiner 重写
                    ▼
          终止：全部达标 / 平均分提升 < 2（收益递减）/ 最大迭代
```

相比单一评审员：单一提示词评审多个维度会注意力稀释（每个维度都浅尝辄止）；专职评审各自深入，且**分维度打分让"哪里最弱、改了有没有用"变得可度量**——轨迹数据可以直接指导下一轮优先改哪个维度。

### 6.6 提示词工程是影响智能体最终效果的关键技术。本章展示了多个精心设计的提示词模板。请分析:

### 6.6.1 对比 ReAct 提示词和 Plan-and-Solve 提示词，它们显然存在结构设计上的明显不同，这些差异是如何服务于各自范式的核心逻辑的？

| 结构要素       | ReAct 提示词                                                                                | Plan-and-Solve 提示词                                                                      |
| -------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 核心交付物     | **每轮一次决策**（Thought+Action 对）                                                       | 规划器：**一次性完整计划**；执行器：**单步结果**                                           |
| 格式部分的角色 | 行动协议——定义机器可解析的指令格式（`Tool[input]`/`Finish[...]`），是整个机制能否运转的命脉 | 数据协议——计划必须是 Python 列表（供 `ast.literal_eval` 解析），是计划能否被程序执行的前提 |
| 动态上下文     | `{history}` 无限增长的行动-观察轨迹，**每轮重新注入**                                       | 规划器无 history；执行器注入 原问题+**完整计划**+历史结果+当前步骤                         |
| 工具清单       | 常驻（每轮都要做工具决策）                                                                  | 不存在（纯推理范式，无需工具）                                                             |
| 位置感设计     | 无——每轮都是"当下"                                                                          | 执行器明确告知"当前是第几步、前面已完成什么"——计划作为**常驻宪法**防止执行偏航             |

**差异如何服务核心逻辑**：ReAct 的智能体是**串行决策器**，提示词的一切设计（格式规约、工具清单、history 注入）都在保证"这一步的决策可解析、可执行、有依据"；Plan-and-Solve 的智能体是**结构化流水线**，提示词的核心任务是把非结构化的问题变成结构化计划（规划器），再让每次执行都锚定在结构上不跑偏（执行器把完整计划与历史结果作为上下文，牺牲 token 换取目标一致性）。一个把复杂度花在"格式鲁棒"，一个把复杂度花在"结构保持"。

### 6.6.2 在 Reflection 提示词中，我们使用了"你是一位极其严格的代码评审专家"这样的角色设定。尝试修改这个角色设定（如改为"你是一位注重代码可读性的开源项目维护者"），观察输出结果的变化，并总结角色设定对智能体行为的影响。

| 评审员                        | 算法向关键词命中 | 可读性向关键词命中 | 给出的"改进后代码"                                                                |
| ----------------------------- | ---------------- | ------------------ | --------------------------------------------------------------------------------- |
| A：极其严格的算法效率专家     | **13**           | 3                  | **重写为埃拉托斯特尼筛法**（O(n√n)→O(n log log n)），附带试除法改良版             |
| B：注重可读性的开源项目维护者 | 1                | **6**              | **保留试除法算法不变**，只做语义化命名、加 docstring、类型注解、`for...else` 重构 |

**结论**

1. **角色决定关注维度**：两个评审看到的是同一段代码，但"看见的问题"完全不同——A 看见复杂度，B 看见命名。角色设定相当于给模型装了**注意力过滤器**。
2. **角色决定改进方向**：更关键的是"改进后代码"的分叉——A 换了算法，B 算法原地不动只改表达。角色不仅影响"说什么"，还影响"做什么"。
3. **角色有盲区**：B 全程没有建议换筛法（可读性角色的盲区），A 只在末尾捎带提了一句命名。**没有哪个角色能看到全部问题**——这正是 6.5.3 需要"多维度专职评审"而不是单评审员的原因。
4. **实践含义**：角色设定本质是对评审标准的隐式编程（隐式 reward shaping）。设计 Reflection 系统时，角色必须与业务目标对齐（性能敏感的代码库用 A，开源协作的代码库用 B），且需要多角色互补。

### 6.6.3 在提示词中加入 few-shot 示例往往能显著提升模型对特定格式的遵循能力。请为本章的某个智能体尝试添加 few-shot 示例，并对比其效果。

1. **格式层面**：g-deepseek-flash 对这个协议的零样本遵循已经很好（0 次解析失败），few-shot 没有体现出格式修复价值——这符合预期：**few-shot 的格式收益在弱模型/复杂协议/多工具场景下才显著**（q2 的压力测试已经展示了格式一旦崩坏正则方案的后果）。
2. **行为层面（意外的增益）**：零样本把 `(123+456)×789/12` **拆成 3 次串行工具调用**（先 123+456，再 ×789，再 /12），而少样本组模仿了示例中"整表达式一次传入"的做法，1 次调用完成——**步骤数减半，LLM 调用从 4 次降到 2 次**。few-shot 不仅教格式，还教**工具的使用粒度与习惯**，这直接影响成本与延迟。
3. **代价与风险**：示例占用的 token 每次调用都要支付；且模型会过度模仿示例细节（示例用 `*` 它就用 `*`、示例怎么分段它就怎么分段）——如果示例本身有坏习惯，会被放大。示例要**最小、正确、贴近真实任务**。

### 6.7 某电商初创公司现在希望使用"客服智能体"来代替真人客服实现降本增效，它需要具备以下功能:

- 理解用户的退款申请理由
- 查询用户的订单信息和物流状态
- 根据公司政策智能地判断是否应该批准退款
- 生成一封得体的回复邮件并发送至用户邮箱
- 如果判断决策存在一定争议（自我置信度低于阈值），能够进行自我反思并给出更审慎的建议

此时作为该产品的负责人:

### 6.7.1 你会选择本章的哪种范式（或哪些范式的组合）作为系统的核心架构？

**选择：ReAct 为主干 + Reflection 做争议决策复核 + 编排层（Orchestrator）兜底**（即 6.1.3 混合架构在具体业务上的落地）：

```
用户退款申请
   │
   ▼
① ReAct 阶段：查询订单/物流/政策（工具调用）→ 输出结构化初判
   {approve, reason, confidence}
   │
   ▼
② 置信度门控：confidence < 70 ？──否──► 直接进入 ③
   │是
   ▼
   Reflection 阶段：质检员角色复核 → 修订决策（可标记 escalate=转人工）
   │
   ▼
③ 邮件生成（独立 LLM 步骤，语气约束）→ send_email 工具发送
```

选型理由：退款处理的核心是**基于外部事实（订单/物流/政策）的决策**，非 ReAct 不能获取事实；而"争议决策"的质量要求高、频次低，用置信度门控触发 Reflection 恰好把贵的机制花在少数 case 上（成本分级）；Plan-and-Solve 不合适——退款是信息收集型任务而非多步结构化任务，没有"计划"可言。

### 6.7.3 如何设计提示词来确保智能体的决策既符合公司利益，又能保持对用户的友好态度？

**决策提示词（ReAct 阶段）**——"既不轻易承诺，也不无理由拒绝"直接写进指令；**置信度评分纪律**单独成段："只有当决策完全落在政策的明确条款内、无需任何酌情裁量时，才允许给出高分(≥70)；凡是涉及折中方案、需要人工复核、政策存在解释空间或依据不足的情况，confidence 必须低于70"。这段纪律是实测迭代出来的：没有它时模型对争议 case 自评 90 分，Reflection 永远不会被触发——**让模型自报置信度时，必须同时给出校准规则，否则门控形同虚设**。

**反思提示词（质检员）**——角色是"资深客服质检员"；核心原则："宁可标记人工复核，也不要在有争议时自动批准或拒绝高价值订单"——把公司利益（避免错误放款/错误拒绝引发的客诉）编码为价值排序；输出强制 JSON 且新增 `escalate` 字段。

**邮件提示词**——三重约束："真诚友好、共情用户；**同时维护公司政策，不做过度的承诺或补偿暗示**；如决策为'需人工复核'，请告知用户专属顾问将在1个工作日内跟进"。实测两封邮件（批准/转人工）语气都符合：道歉共情、讲清政策依据、明确下一步动作，无过度承诺。
